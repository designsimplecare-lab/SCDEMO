Patient Chat QA Agent& End-to-End Testing Plan
SimpleCare / Patient Booking Experience
Purpose: create an AI QA agent that experiences the product like a real patient and systematically tests the complete conversational booking journey.
Heading1: 1. Objective
The QA agent should test the patient experience from the moment a patient lands on the homepage through finding care, selecting a doctor and appointment window, registering or signing in, and reaching a clear confirmation.
The agent should test more than technical functionality. It should evaluate whether the experience is understandable, consistent, recoverable, and aligned with the patient's mental model.
Heading1: 2. What the QA Agent Is Responsible For
ListBullet: Act as a real patient rather than as a developer.
ListBullet: Start from the actual patient entry point and use the interface naturally.
ListBullet: Use both provided UI options and realistic free-text language.
ListBullet: Test happy paths, alternate paths, edge cases, errors, interruptions, and changes of intent.
ListBullet: Verify that the conversation maintains context throughout the journey.
ListBullet: Verify that the chat and UI stay synchronized.
ListBullet: Identify UX issues even when the system technically works.
ListBullet: Capture reproducible evidence for every issue.
ListBullet: Separate product/UX issues from technical defects when reporting findings.
Heading1: 3. QA Agent Setup
Create the QA agent with the following role definition:
You are an autonomous patient-experience QA agent. Your job is to test this healthcare product as a real patient. Do not assume the intended workflow. Do not skip steps because you know how the product is supposed to work. Interact with the product, observe what happens, and make decisions based only on what a normal patient would reasonably understand.

Heading1: 5. Agent Rules
ListNumber: Do not assume the user knows the correct terminology.
ListNumber: Prefer natural patient behavior over idealized test behavior.
ListNumber: If a button or message is unclear, treat that uncertainty as a finding if it affects task completion.
ListNumber: Do not silently work around confusing UI. Record the confusion.
ListNumber: When an action fails, attempt a reasonable recovery before abandoning the flow.
ListNumber: When changing intent, behave like a real patient who changed their mind.
ListNumber: Do not report a missing feature as a bug unless the requirement or UI indicates that it should exist.
ListNumber: Do not invent expected behavior. Use the supplied requirements/Figma/workflow when an expected behavior is needed.
ListNumber: Capture screenshots or other evidence at the point of failure whenever possible.
ListNumber: Do not expose real patient data. Use approved test accounts/data only.

Heading1: 11. UX / Mental-Model QA
The agent must evaluate whether the product makes sense to a patient, not only whether the underlying functionality works.
ListBullet: Does the patient understand what the current step is?
ListBullet: Does each assistant message make the next action obvious?
ListBullet: Does terminology stay consistent?
ListBullet: Does the experience clearly distinguish doctor selection from appointment selection?
ListBullet: Does the patient understand why registration is required?
ListBullet: Is it clear whether an appointment is only being viewed or has actually been booked?
ListBullet: When the patient changes their mind, does the interface reflect the new intent?
ListBullet: Does the interface preserve context between chat messages and cards?
ListBullet: Are important confirmations visually and verbally clear?
ListBullet: Could a first-time patient become stuck without knowing what to do next?
Heading1: 12. Visual / UI QA
ListBullet: Compare implemented screens against approved Figma when available.
ListBullet: Check spacing, hierarchy, typography, icons, buttons, cards, and states.
ListBullet: Check hover, selected, disabled, loading, empty, and error states.
ListBullet: Check that appointment cards accurately communicate date, time, doctor, and availability.
ListBullet: Check that chat messages and UI cards appear in the correct sequence.
ListBullet: Check responsive behavior at the supported viewport sizes.
ListBullet: Flag visual inconsistencies that materially affect comprehension or interaction.

Heading1: 14. Severity Definitions
Severity
Definition
Critical
Patient cannot complete a core booking flow, incorrect appointment/patient outcome, or serious safety/privacy issue.
High
Major workflow is blocked or the patient can reasonably select/understand the wrong outcome.
Medium
Workflow can continue, but there is meaningful confusion, inconsistency, or repeated effort.
Low
Minor visual/content/interaction issue with limited impact on task completion.

Do not skip steps because you know what the system is supposed to do. Use only information available to a normal patient plus the supplied requirements and Figma references.Test the homepage chat, patient intent recognition, doctor selection, appointment selection, new/existing patient paths, registration/authentication, confirmation, errors, empty states, loading states, back navigation, changes of intent, and unexpected inputs.Run all defined test scenarios. Use both UI controls and realistic free-text language.For each scenario:1. State the patient goal.2. Execute the flow.3. Record what happened.4. Heading1: 17. Suggested Execution Order
ListNumber: Set up staging environment and approved test accounts.
ListNumber: Give the QA agent the staging URL, requirements, Figma references, and test data.
ListNumber: Run the three primary happy paths: new patient, existing patient, and quick-book.
ListNumber: Run family-doctor and specific-doctor flows.
ListNumber: Run natural-language and ambiguous-intent tests.
ListNumber: Run change-of-mind and back-navigation tests.
ListNumber: Run registration/authentication edge cases.
ListNumber: Run no-availability and error scenarios.
ListNumber: Run visual/UI comparison checks.
ListNumber: Generate the consolidated QA report.
ListNumber: Review high-impact findings with product/design/engineering.
ListNumber: Fix and rerun the failed scenarios as regression tests.
Heading1: 18. Regression Test Set
After fixes are made, the agent should rerun every scenario that previously failed plus the three core booking paths. A fix should not be considered complete until the original reproduction steps pass and the surrounding journey still works.
